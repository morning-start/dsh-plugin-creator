# 端到端 debug 复盘（这个项目真实踩过的坑）

> 每条都给：**现象 → 证据 → 根因 → 处置 → 可复用判据**。
> 值钱的是最后一条：下次遇到同类现象，不用重新推理。

## 1. 桌面端被"顶掉"（宿主反复退出）

- **现象**：用着用着弹「应用无法启动或已意外停止」，宿主 `exited with 4294967295`；几分钟内连崩三次。
- **证据**：`%APPDATA%\@deepseek-ai\dsh-desktop\logs\crash-*-host.log` 里 `dsh desktop host exited with 4294967295`；
  同期的测试脚本里写着 `DeepSeek Harness.exe … dsh-desktop-host\lib\cli.js --profile <测试 profile>`。
- **根因**：测试脚本起的是**桌面端自己的宿主二进制**，还共用同一个 `DSH_HOME`。桌面端是单实例语义，
  第二个宿主把第一个顶掉。
- **处置**：测试实例只用运行时 CLI 起 web（`dsh --profile <p> --port <p> --no-open`），并换 `DSH_HOME`。
- **判据**：**任何测试脚本里出现 `dsh-desktop-host` 或 `DeepSeek Harness.exe`，一律视为事故源**，改回 `dsh`。

## 2. `EADDRINUSE`

- **现象**：实例起不来，日志一行 `EADDRINUSE`；有时"起来了一半"（路由挂了但页面打不开）。
- **根因**：端口写死（3080/5199/5200/5202 都被用过），或上一个实例没退干净。
- **处置**：`--port 0` 让系统分配，或每次用新口；停实例前先按端口确认是自己那个。
- **判据**：**端口是消耗品，不是配置**。看到 `EADDRINUSE` 先换口，别急着杀进程。

## 3. `N required plugins did not activate`

- **现象**：宿主起来了，但某些入口/路由整块消失；日志里一行 `2 required plugins did not activate`。
- **根因**：组合树里某行插件加载失败（依赖没装、`lib` 没构建、patch 覆盖写错），宿主选择"带伤启动"。
- **处置**：`--dump-config` 看那几行 → 单独启动看首次异常 → 装依赖 / 重建 `lib` / 修 patch。
- **判据**：**入口消失优先怀疑"插件没激活"，而不是"前端渲染坏了"**（后者页面会有 DOM，前者整块没有）。

## 4. 会话被占用 / 面板说"没有绑定工作区"

- **现象**：面板/工具返回「当前会话没有绑定工作区」，或两个实例看到不同的会话列表。
- **根因**：会话类能力走 `agents.get(sessionId)`，只认**本进程活会话**；共享 `DSH_HOME` 时两个实例的会话互不可见，
  写者锁还会互抢。
- **处置**：隔离 `DSH_HOME`；自动化时用 gateway `session.create` 造本进程活会话。
- **判据**：**"会话"是进程内对象，不是磁盘上的文件**——磁盘上的会话记录不能当活会话用。

## 5. `WRITER_LEASE_LOST`

- **现象**：读/写接口返回 `WRITER_LEASE_LOST`，`details` 带 `pid` / `owner` / `renewedAt`。
- **根因**：单写者租约；另一个活进程正持有该项目的写锁（常见于桌面端和你起的实例同时指向同一仓库）。
- **处置**：测试用工作区**副本**并删副本里的 `state/writer.lock`；或停掉另一个写者。
- **判据**：**删锁只能删副本里的**；删真实项目的锁 = 制造双写。

## 6. 面板 401 / 403

- **现象**：`401 MT_UNAUTHENTICATED`（没带会话 cookie）或 `403 MT_UNTRUSTED_HOST`（反代/局域网）。
- **处置**：401 → 用实例启动行打印的 `?token=` 铸 cookie（**仅对自己起的实例**）；403 → 给实例加 `--trusted-host`。
- **判据**：**401 是准入在生效，不是插件坏了**；想验证路由契约就先把 cookie 带上。

## 7. 客户端 bundle：不要猜单插件路径

- **现象**：`GET /plugins/<包名>/client.js` 返回 404，误判"客户端没发出来"。
- **根因**：宿主把多个插件客户端合并成一条 URL（`plugins/??a/client.js,b/client.js&rev=…`）。
- **处置**：从首页 HTML 里取出那条 URL 原样请求，再断言内容包含你仓库 `client/client.js` 的特征串。
- **判据**：**拼路径必错，抄 URL 才对**。

## 8. Inspect 的宿主归属

- **现象**：在隔离实例里装了插件，Inspect 查不到它的 slot，误判"没生效"。
- **根因**：`cordis_inspect_*` 绑定在**发起调用的 agent 所在的宿主**，不是你想的那个实例。
- **处置**：隔离实例靠 HTTP 探针 + 人眼；Inspect 只用于验证"当前宿主"的活注册。
- **判据**：**Inspect 回答的是"我这里有没有"，不是"那边有没有"**。

## 9. "装了但入口不见"（最常见误判）

- **现象**：用户说装了插件，界面里没有入口。
- **真实原因（本项目）**：插件装在 `web` profile，用户看的是 `desktop` 实例；而那次 `dsh web` 自己没起来
  （`EADDRINUSE` + 插件激活失败）。**插件本身是好的**。
- **处置**：三问——插件在哪个 profile？你看的是哪个实例？那次启动成没成？
- **判据**：**先确定"该有"和"在看"是不是同一个实例，再查代码**。

## 10. `session.create` 的参数形状

- **现象**：`gateway/arguments-invalid` 或 `Remote payload must contain exactly one plain-object args field`。
- **根因**：RPC 帧要求 `payload.args` 恰好是一个对象，且业务参数按"具名参数"嵌一层。
- **可用形状**：`payload: { args: { request: { cwd } } }`（`session/create`）。
- **判据**：**报错里已经告诉你形状错了**，改形状，不要改插件。

## 11. `link:` 安装不跑 `prepack`

- **现象**：改完源码重启，行为还是旧的。
- **根因**：`link:` 只建立链接，不执行包的 `prepack`；宿主加载的是 `lib/`（构建产物）。
- **处置**：改完 `src/` 必须重建 `lib/`；客户端改动另算（硬刷新即可）。
- **判据**：**"改了没反应"先问"构建了吗"**，再问"我改的是宿主那半还是客户端那半"。

## 12. 深色与作用域：设计稿 CSS 不能直接搬

- **现象**：设计稿里好看的样式，搬进宿主后深浅色不对/作用域串味。
- **根因**：设计稿给静态页画，作用域是 `[data-slot="main"]`、深色靠 `html[data-theme="dark"]`；
  宿主里插件有自己的根节点。
- **处置**：服务端组装样式时把作用域改写成插件根（本项目 `[data-myteam]`），深色段改成
  `html[data-theme="dark"] [data-myteam]`；变量分两层：宿主 alias（`--dsw-*`）→ 插件语义（`--mt-*`）。
- **判据**：**样式一定由"服务端拼 + 改写作用域"提供**，客户端只写结构类名，不写色值。

## 13. 假失败：管道截断与编码

- **现象**：`npm pack --dry-run | Select-Object -Last 5` 退出码非零，但内容是对的；日志正则匹配不上。
- **根因**：PowerShell 管道提前截断 → 上游收到管道关闭；`cmd > log` 写 UTF-16LE（`FF FE`）。
- **处置**：以 `npm run prepack` 等的**退出码**为准；读日志先按 BOM 判编码（`FF FE` → utf16le）。
- **判据**：**先怀疑工具链，再怀疑结论**；退出码、编码、截断各查一遍。

## 14. 隔离 home 里没有模型凭据

- **现象**：隔离实例里面板能读能写，但 agent 回合失败/无模型；或输入框右下角「请选择模型」是空的、
  消息根本发不出去、会话建不出来。
- **根因**：`DSH_HOME` 换了，`.credentials.yaml` 是新的空骨架。**它不是不存在，是 0 字节** ——
  所以「文件在」不能当凭据在的证据。
- **处置**：需要 agent 时把真实 home 的 `.credentials.yaml` 复制过去，或在那个实例里配一次；
  配完**保留这个 home**（见第 15 条）。
- **判据**：**"隔离"包括凭据**；读面板不需要模型，跑 agent 需要。
  检查方式是 `Get-Item .credentials.yaml | Select Length`，0 就是空。

## 15. 每次重建隔离 home —— 把最贵的东西一起删了（本次最值钱的一条）

- **现象**：前天/上一轮还能「发条消息就有会话」，这次同一个脚本跑不出会话；
  看起来像插件退化，实际是环境被自己清了。
- **证据**：脚本里写着 `rmSync(ISO, { recursive: true, force: true })`，每次运行都执行；
  重建后 `package.json` 需要重新 `plugin add`（pnpm 又要装一遍），
  手动加的模型凭据也没了。
- **根因**：把 home 当成「一次性的测试产物」，而它其实是**按插件长期存在的开发环境**。
  里面有几样东西重建代价很大：pnpm 安装、**用户手动加的模型凭据**、profile 里的插件版本、登录态。
- **处置**：
  1. home 路径按**插件**固定（如 `<repo>/tmp/iso-home`），写进脚本常量；
  2. 脚本默认**复用**，加 `--reuse-home`（或反过来：默认复用，加 `--fresh` 才重建）；
  3. 输出里**打印当前是「复用」还是「重建」**——不打印的话，这类问题永远查不出来；
  4. 只有怀疑 home 被搞脏、或要演示全新安装时才重建。
- **判据**：**"干净"不是美德，是成本**。日常迭代复用；重建前先问"我会丢掉谁的凭据/安装"。

## 16. `.cmd` 里 `!VAR!` 在括号块里没展开（而且这个坑能潜伏很久）

- **现象**：`dsh plugin add "!LINK!"` 拿字面量 `!LINK!` 去 npm 上找，报
  `ERR_PNPM_FETCH_404 … !LINK!: Not Found`。
- **根因**：变量赋值和读取都写在 `if (...)` 括号块里。`%VAR%` 在整块解析时就展开（此时还没赋值），
  `!VAR!` 需要延迟展开真正生效。两者在这个位置都不对。
- **为什么潜伏很久**：这段逻辑包在 `if not exist <profile> (...)` 里。
  之前每次运行都走「profile 已存在 → 跳过整块」，**那几行从来没执行过**；
  第一次真的执行（换了新 home）才炸。**没执行过的分支 = 没验过的分支。**
- **处置**：改成扁平结构（`if exist … goto :label`，标签在文件末尾），或把这几步抽到独立 `.cmd` 里用 `call` 调；
  在扁平段里用纯 `%VAR%` 就对了。
- **判据**：**`!VAR!` 只在你确定延迟展开已开、且不在解析期取值时用**；跨「首次/非首次」两条分支的脚本，
  两条路都要真跑一遍。

## 17. `.cmd` 里直接调另一个 `.cmd` 不加 `call`

- **现象**：启动脚本打印了第一行「creating profile…」就结束了，后面全没执行；
  外层只看到「实例没起来」，没有任何报错。
- **根因**：批处理之间**不加 `call` 直接调用，是控制权转移（不返回）**。子脚本结束后整个流程就结束了，
  后续行一行都不执行，退出码还是子脚本的。
- **处置**：调用另一个 `.cmd`/`.bat` 一律写 `call "%DSH%" ...`。
- **判据**：**脚本"静悄悄地少做了一半事"，先看有没有漏 `call`**。

## 18. `.cmd` 被存成 LF 换行 → 标签找不到

- **现象**：`call :create_profile` 报「系统找不到指定的批处理标签」，
  但这个标签明明在文件里，而且同样结构的最小复现文件却正常。
- **根因**：文件是 LF-only。cmd.exe 解析批处理默认按 CRLF；LF-only 下标签查找会失败。
  用 Node/Python 脚本改写 `.cmd` 时很容易把 CRLF 写成 LF。
- **处置**：`.cmd`/`.bat` 一律 CRLF；仓库里加 `.gitattributes`：
  ```
  *.cmd  text eol=crlf
  *.bat  text eol=crlf
  ```
  否则 `* text=auto eol=lf` 会在检出时把 `.cmd` 转成 LF，问题只在别人的机器上出现。
- **判据**：**改过 `.cmd` 就查一次换行**（`(text.match(/\r\n/g)||[]).length` 与 LF-only 计数）；
  纯 ASCII 也一样——中文注释写进 `.cmd` 还会因为代码页把行拆坏。

## 19. 隔离 home **不**隔离工作区（默认工作区指向用户的真实目录）

- **现象**：换了 `DSH_HOME`，以为全隔离了，但插件在会话里报「项目数据版本为 1，当前代码只支持 v2」
  —— 而你的副本里明明是空的/是 v2。一看路径，读的根本不是副本。
- **证据**：`$ISO\storages\workspace.json` 里 `tables.workspaces[*].path` 写着
  `C:\Users\<user>\Documents\deepseek-harness\default-workspace`（用户的真实目录）；
  那个目录下有一份 `schemaVersion: 1` 的 `.dsh-myteam`（2026-11 之前建的）。
- **根因**：`DSH_HOME` 隔离的是会话 / 凭据 / profile / `storages`，
  **工作区（会话 cwd）是独立登记的绝对路径**。隔离 home 新建时宿主会自建一个默认工作区，
  路径落在用户的 `Documents` 下 —— 于是"隔离实例"的会话跑在用户的真实目录上。
  再叠上「插件只支持 v2、那份是 v1」，表现就是每一栏都显示未初始化。
- **处置**：起实例**之前**改隔离 home 里的 `storages/workspace.json`，把每个
  `workspaces[*].path` 指向仓库内的副本目录（改的是我们自己那份 home，不动用户状态）：
  ```js
  const wsJson = JSON.parse(readFileSync(join(ISO, 'storages', 'workspace.json'), 'utf8'))
  for (const entry of Object.values(wsJson.tables?.workspaces ?? {})) {
    entry.path = WS          // <repo>/tmp/iso-ws
    entry.title = 'iso-workspace'
  }
  writeFileSync(join(ISO, 'storages', 'workspace.json'), JSON.stringify(wsJson, null, 2) + '\n')
  ```
  然后确认界面上工作区名变成了你的副本名。
- **判据**：**"隔离"要数三样：home、profile/端口、工作区**。少第三样，测试就是在用户的项目上跑。
  验证方式是看面板标题里的项目名是不是你的副本名。

## 20. 用 JS 改 `value` 打字对 React 受控输入无效

- **现象**：给输入框设了 `value` 并派发 `input` 事件，`querySelector` 也能找到元素，
  但**界面里 placeholder 还在**（文字没进去），回车也没反应 —— 于是"发不出消息、建不出会话"。
- **根因**：这条路径对普通受控 `<input>` 有时有效，但对**富文本 / contenteditable / 自定义编辑器**
  （本项目底部输入框就是个 `DIV[contenteditable]`）无效：框架的受控逻辑不认直接赋值。
- **处置**：用 CDP 走**真实输入路径**——
  1. `Input.dispatchMouseEvent`（`mousePressed` + `mouseReleased`）点进输入框；
  2. `Input.insertText`（走 IME 路径）输入文字；
  3. `Input.dispatchKeyEvent`（`keyDown` + `keyUp`，`key/ code / windowsVirtualKeyCode: 13`）回车。
  并在输入后**回读一次**输入框内容（`value` 或 `textContent`）确认真的进去了，再发。
- **判据**：**"我点了/我输了"要有回读证据**；`placeholder` 还在就是没进去。


## 心得（七条，写在这里是为了下次少走弯路）

1. **先划边界，再写代码**：home / profile / 端口 / 工作区，四个边界不清楚，后面所有现象都不可解释。
2. **第一手证据只有三种**：组合树（`--dump-config`）、宿主日志、HTTP 响应体。别用"我记得""应该"。
3. **对账优于观感**：计数要和磁盘比，文件要 mtime + 内容一起看，"页面有东西"不算验证。
4. **只停自己的东西**：按端口/PID 停，不按进程名；不认识的进程不碰。
5. **把"没验到"写出来**：视觉、暗色、窄宽、真实用户路径——写清楚是"没验"还是"验过"，比补一句"应该没问题"值钱。
6. **环境复用，别每次重建**：隔离 home 是按插件长期存在的开发环境，不是一次性产物。
   里面最贵的是**别人手动配的东西**（模型凭据、登录态）——`rm -rf` 一下，下次的失败会伪装成"插件坏了"。
7. **"隔离"要数三样**：home、profile/端口、**工作区**。少第三样，测试就悄悄跑在用户的项目上
   （第 19 条就是只做了前两样，结果读到用户的 v1 数据、每栏都显示未初始化）。

## 修一次 bug 的复盘也要能变成规则

第 1–20 条都是"跑起来才看得到"的坑，写在这里供人反查。但有一类坑**能在写代码时就静态查出来**——
比如"交给会话的消息没有 id"：写入路径不校验、加载路径强制要求，一条没 id 的消息会让用户下次打开时整段会话打不开。
这类不该只写进复盘，要写成 `checks.json` 的一条规则，让 `check-project` / `check-bundle` 每次跑都替你看着。

判断标准很简单：**这件事能不能在不启动实例的前提下、扫源码或文件就判死？**

- 能 → 写进仓库根的 [`errors/`](../../../errors/README.md)，加一条规则类型，在 `try-checks` 里加"反例先红"的用例。
- 不能（运行时、环境、渲染）→ 留在这个文件里，写清判据。

两边都写会漂移；只写复盘不改规则，同一个坑会被人再踩一次。这一条是 2026-11 那次 `lacks an identified message` 事故的直接教训。
