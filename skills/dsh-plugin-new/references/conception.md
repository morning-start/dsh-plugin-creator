# 构思：从「我想加点什么」到一个插件形态

这个文件是**自带的兜底清单**。宿主里如果有 `scenario-driven-product-design` 技能，先用它做需求分析（角色、场景、优先级那一套），再回到这里做形态判定；没有就用下面的问题自己走一遍。

目标不是产出产品文档，而是产出**五行决策记录**，让后面的生成和检查有依据。

## 什么时候需要构思

| 用户的说法 | 处理 |
|---|---|
| 「给我建个叫 dsh-plugin-x 的插件，做 Y」 | 字段已经清楚，跳到生成访谈 |
| 「我想让团队协作好一点」「帮我加个能看进度的东西」 | **先构思**：现在还没有形态 |
| 「能不能在插件里加个按钮」 | 半清楚：形态有了（客户端半边），场景和边界没定 |
| 「这个插件要不要做成工具」 | 形态判定问题，直接看下面的表 |

判据：**能不能一句话说出「谁在什么情况下用它、它替掉了现在的什么麻烦」**。说不出，就是还没构思。

## 五个问题（一次问完，别来回磨）

1. **谁用？** 角色 + 他现在的做法。插件通常是给「已经在用 DSH 的人」用的，所以要问的是**他在 DSH 里做什么事时卡住了**，不是泛泛的用户画像。
2. **什么场景？** 2–4 个具体场景，每个写成「当……时，他想……，现在得……（麻烦）」。场景数量超过 4 个，说明这一版太大。
3. **不做什麼？** 明确划出这一版不碰的部分。没有「不做」清单的需求，最后一定会膨胀。
4. **插件形态？** 见下表，这是构思里唯一必须落到技术形态的一步。
5. **先做哪个？** 从场景里挑一个作为第一版，其余进路线图。

## 形态判定表

| 需求特征 | 形态 | 代价 / 注意 |
|---|---|---|
| 模型需要**主动调用**一个动作（查、改、算、发） | **Host 工具** | 工具目录对所有预设可见；要限定范围就得覆写预设 |
| 只是**文案 / 提示词 / 语气** | **预设**（persona 或 instructions） | 不需要工具，改预设配置即可 |
| 用户要在**界面里看到或操作** | **客户端半边**（slot / panel） | 要单独做 UI 插件、注册 slot，验证成本最高 |
| 让某个能力**只在特定模式**可用 | **预设级挂载**（patch 覆写 preset） | patch 不深合并，要整段复述该预设的 plugins，升级 DSH 后需重新同步 |
| 每次会话都要遵守的**规矩 / 流程** | **Skill** 或 agent-instructions | skill 是部署级的，所有预设的会话都会列出来 |
| 只是**开关 / 参数** | **配置**（Config） | 最轻；先做配置，不够再上工具 |

一条需求经常要**两三种形态组合**（工具 + skill、工具 + 预设挂载）。组合时按「最小可用」排：先工具，能跑通再加 skill 教怎么用。

## 输出：五行决策记录

写完给用户复述一遍，点头再生成：

```
目标用户：<角色>，他现在<做法>，卡在<哪里>
核心场景：1) 当…时… 2) 当…时…
边界：这一版做<…>；不做<…>
形态：<工具 / 预设 / 客户端半边 / skill / 配置>，因为<一句话理由>
第一版：只做场景 <n>，其余进路线图
```

这五行直接喂给生成访谈：`description` 从「核心场景」里提炼，「做什么 + 从哪儿触发」自然就有了；`withTool` / `withSkill` 从「形态」来。

## 不要做的事

- **不要在这一步写代码或建目录。** 形态没定就生成，产出的包一定返工。
- **不要跳过「不做什麼」。** 没有边界的插件会长成什么都沾一点的样子。
- **不要把产品分析写成长文档。** 插件通常只需要上面五行；用户要完整分析时，才用 `scenario-driven-product-design` 的完整产出（角色表、场景卡、优先级矩阵）。
- **不要替用户决定形态。** 表格给建议，选择是用户的——尤其是「要不要客户端半边」，那决定验证成本翻几倍。
