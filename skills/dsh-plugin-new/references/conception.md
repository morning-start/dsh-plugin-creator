# 构思：从「我想加点什么」到一个插件形态

**方法来源**：这套流程参考并内化了 `scenario-driven-product-design` 的场景驱动方法——角色表、能力五态、边界八问、两套排序、明确不做。按插件场景做了裁剪：不产出产品文档，不铺四张底图，只保留「决定要不要做、做成什么形状、先做哪个」必需的部分。**不依赖那个技能存在**，它是灵感来源，不是运行时依赖。

## 三条铁律

1. **从痕迹反推，不写想象中的人设。** 「团队需要协作」不是需求；「上周三次因为不知道谁在改哪个文件而重做」才是。用户原话、现有插件的用法、失败记录，都算痕迹。
2. **结论带证据。** 实测 > 日志截图 > 用户原话 > 推断。说「现在做不到 X」之前，先在当前会话里试一次——很多需求 DSH 出厂就有，或者创造模式的工具已经能做。
3. **场景必须能失败。** 写不出失败形态、空态和退出路径的场景，还没被想清楚。

## 什么时候需要构思

| 用户的说法 | 处理 |
|---|---|
| 「给我建个叫 dsh-plugin-x 的插件，做 Y」 | 字段清楚，跳到生成访谈 |
| 「我想让团队协作好一点」「帮我加个能看进度的东西」 | **先构思**：现在还没有形态 |
| 「能不能在插件里加个按钮」 | 半清楚：形态有了，场景和边界没定 |
| 「这个插件要不要做成工具」 | 直接看形态判定表 |

判据：**能不能一句话说出「谁在什么情况下用它、它替掉了现在的什么麻烦」**。说不出，就是还没构思。

## 第一步：角色与入口

不要从「用户是谁」开始，从「谁在什么位置、能做什么」开始。

| 角色 | 是谁 | 从哪进 | 能做什么 | 不能做什么 | 做错了谁收拾 |
|---|---|---|---|---|---|

插件场景里几乎总有三个角色，**必须分开写**：

- **操作者**：人类，点界面、发消息；
- **执行者**：模型，调工具、读文件；
- **被影响者**：可能完全不在场（同事、下一个会话、未来的自己）。

> **操作者 ≠ 执行者** 这条在插件里尤其容易踩：你给模型加了一个「改配置」的工具，人类在界面里却没有对应入口，或者反过来。两者的写面、错误面、可恢复性都不一样。

## 第二步：现有能力五态（最重要的一步）

DSH 的设计原则第一条是「先看创造模式已经有什么」。这一步就是它的判据。

| 态 | 判据 | 处理 |
|---|---|---|
| **通** | 生产入口 → 实现全链有调用，且真跑过一次 | 别重写，包一层或直接用 |
| **半** | 后端/工具存在，但没有入口，或入口是空实现 | 优先接线，而不是新写 |
| **假** | 文档、注释、测试声称有，生产代码零调用 | 先拆假象，再决定补不补 |
| **断** | 有入口，但语义不通（分支提前返回、参数丢失、状态卡死） | 修流程，不是加按钮 |
| **无** | 真没有 | 进路线图，按频次排 |

**没有真跑过入口，不得标「通」。** 文档和 PRD 都不算证据。

这一步的产出往往直接砍掉一半需求：你以为要写的东西，创造模式已经有了，只是入口藏得深。

## 第三步：场景枚举

场景不是头脑风暴，是**角色 × 阶段 × 意图**铺出来的。插件通常只需要 5–8 条，别铺满网格。

按这八组各问一遍，每组至少想一下「有没有」：

| 组 | 插件里的问法 |
|---|---|
| 首次上手 | 装好之后第一次怎么用？三步内能不能拿到第一个有价值的结果？ |
| 日常主链路 | 最高频的那次调用，落在哪个工具 / 哪个界面？ |
| 卡住 | 它没按预期工作时，用户看到什么？怎么知道是插件的问题？ |
| 调整 | 用了一半要改参数 / 换范围，怎么退、怎么续？ |
| 暂停 | 关掉这个插件，正在做的事会怎样？ |
| 切换 | 换会话 / 换预设 / 换工作区，状态丢不丢？ |
| 协作 | 别人的会话会受影响吗？共享的配置、skill、工具目录会不会串？ |
| 配额与成本 | 它花 token / 花时间吗？到上限时用户看到「为什么」还是只有一个数字？ |

再补三类**失败场景**：权限被拒、上游依赖缺失（DSH 版本不匹配、目标目录不存在）、崩溃后恢复。

每条场景写成一行：**当……时，他想……，现在得……（麻烦）**。

## 第四步：边界八问

只对**第一版要做的那个场景**问，不必每条都问：

| 字 | 问法 |
|---|---|
| **空** | 没有输入 / 没有数据时，工具返回什么？空态还是永远转圈？ |
| **重** | 连点两次、重复调用，会不会落两份结果？ |
| **并** | 两个会话同时用，谁赢？有没有锁或幂等？ |
| **权** | 越权调用返回什么？拒绝时有没有告诉用户该走哪个出口？ |
| **断** | DSH 升级、依赖缺失、目标不存在，是卡死还是有诊断？ |
| **慢** | 超时 / 网络断，静默失败还是明确报错？ |
| **大** | 100 个文件 / 10 万 token 时还成立吗？ |
| **旧** | 旧数据没有新字段，重放会不会炸？ |

## 第五步：形态判定

这是构思里唯一必须落到技术形态的一步。

| 需求特征 | 形态 | 代价 / 注意 |
|---|---|---|
| 模型需要**主动调用**一个动作（查、改、算、发） | **Host 工具** | 工具目录对所有预设可见；要限定范围就得覆写预设 |
| 只是**文案 / 提示词 / 语气** | **预设**（persona 或 instructions） | 不需要工具，改预设配置即可 |
| 用户要在**界面里看到或操作** | **客户端半边**（slot / panel） | 要单独做 UI 插件、注册 slot，验证成本最高 |
| 让某个能力**只在特定模式**可用 | **预设级挂载**（patch 覆写 preset） | patch 不深合并，要整段复述该预设的 plugins，升级 DSH 后需重新同步 |
| 每次会话都要遵守的**规矩 / 流程** | **Skill** 或 agent-instructions | skill 是部署级的，所有预设的会话都会列出来 |
| 只是**开关 / 参数** | **配置**（Config） | 最轻；先做配置，不够再上工具 |

一条需求经常要**两三种形态组合**（工具 + skill、工具 + 预设挂载）。组合时按「最小可用」排：先工具，跑通了再加 skill 教怎么用。

## 第六步：排序，两套别混用

| 你在决定什么 | 主排序 | 约束 |
|---|---|---|
| **新插件先做什么** | 频次优先（一天用几次） | 无依赖、纯读的先做 |
| **已有插件先修什么** | 伤害优先（数据污染 > 卡死 > 误导 > 不顺） | 改动风险、依赖关系做约束 |

**一条否决**：被权限或部署范围否决的需求，不进第一版。要么换入口，要么写进「明确不做」。

## 输出：七行决策记录

写完复述给用户，点头再生成：

```
目标用户：<角色>，他现在<做法>，卡在<哪里>
核心场景：1) 当…时… 2) 当…时…
现有能力：<通/半/假/断/无>——所以这一版<复用/接线/新写>
边界：这一版做<…>；不做<…>
形态：<工具 / 预设 / 客户端半边 / skill / 配置>，因为<一句话理由>
第一版：只做场景 <n>，验收是<能观察到什么>
不做：1) <…> 2) <…> 3) <…>
```

这七行直接喂给生成访谈：`description` 从「核心场景」提炼，「做什么 + 从哪儿触发」自然就有了；`withTool` / `withSkill` 从「形态」来。

## 不要做的事

- **不要在这一步写代码或建目录。** 形态没定就生成，产出的包一定返工。
- **不要跳过「现有能力五态」。** 十有八九，需求的一半已经在 DSH 里了，只是入口不在你以为的地方。
- **不要跳过「不做」。** 没有边界的插件会长成什么都沾一点的样子；「不做」表的作用是防止每轮重新讨论。
- **不要写成产品文档。** 插件只要七行；用户要完整分析时，才展开成场景卡、优先级矩阵那一套。
- **不要替用户决定形态。** 表给建议，选择是用户的——尤其「要不要客户端半边」，它决定验证成本翻几倍。
