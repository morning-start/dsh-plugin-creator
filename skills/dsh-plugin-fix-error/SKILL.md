# 按卡片修一个插件错误

这个技能的形状是**先认领、再修**。

`errors/` 里一条一个文件，**前面是卡片，后面是正文**：

| | 内容 | 谁读 |
|---|---|---|
| **卡片**（frontmatter） | 名称、原因、系统原文、位置、后果、修法简述 | 先读它，判断「这是不是我的错」 |
| **正文** | 机制、为什么当时不报、完整修复步骤、边界 | 确定是它之后再读 |

卡片是**索引**，正文是**解释**。两者不重复：卡片让你三秒内决定要不要继续，正文让你真正改对。不要只读卡片就动手——卡片里的「修法」是一句话，够定位不够改对。

## 第 1 步：从错误文本找到卡片

不要凭印象猜是哪类错。用脚本查（下面的命令在 **dsh-plugin-creator 检出**里跑；在别的项目里加 `--root <那个项目>`）：

```powershell
node scripts/list-errors.mjs --root .                                  # 全部卡片
node scripts/list-errors.mjs --root . inject                           # 按 id / 名称 / 系统原文 过滤
node scripts/list-errors.mjs --root . --json                           # 机器可读
```

过滤是**对 `matches`（系统原文）也做的**，所以直接把报错里最稳定的一段丢进去就行：

```powershell
node scripts/list-errors.mjs --root . "is not declared in inject"
node scripts/list-errors.mjs --root . "lacks an identified message"
```

> 挑**稳定**的那一段。行号、路径、seq、session id 都每台机器不同，别拿它们当关键词。

命中之后：

1. 读它的**正文**（`errors/<id>.md`），不是只读卡片；
2. 确认「什么时候会踩」那节描述的触发条件**和你眼前的情况一致**。不一致就是另一条坑，回到第 1 步。

## 第 2 步：用卡片上的 `check` 拿到精确位置

卡片的 `check` 字段指向一条规则类型。跑它，而不是靠肉眼找：

```powershell
node scripts/check-project.mjs --only <rule>     # 规则在 checks.json 里，通常是 <area>:<thing> 形式
node scripts/check-project.mjs                    # 不知道是哪条就先全跑
```

输出里每条都带 `file:line` 和一句人话。**这一步的产物是坐标，不是判断**——报告说某行有问题，你仍然要打开那行看它是不是真的（规则也可能误报，误报要回去修规则，见第 6 步）。

## 第 3 步：按正文修，不按卡片修

正文的「怎么修」才是能直接抄的。三条硬要求：

- **顺着现有写法改**，不引入新机制。仓库里已有同类构造就用它，不要另搭一套；
- **只改出错的那一处**。顺手重构会把「修一个错」变成「审一次代码」，回归范围失控；
- **反例要留在文档和测试里**。删掉反例等于删掉教训，下一次同样的坑没人认得。

改完立刻重跑第 2 步那条规则，确认它绿：

```powershell
node scripts/check-project.mjs --only <rule>
```

## 第 4 步：跑全量门禁，不只跑那一条

修好一条规则不等于没弄坏别的。**必须**跑全量：

```powershell
node scripts/check-project.mjs                    # 所有项目规则
node scripts/try-checks.mjs                       # 规则自身的用例（反例仍应报错）
```

如果仓库另有测试套件（`scripts/try-*.mjs`、`npm test`），一并跑完。判据是**全部 exit 0**，不是「我改的那个文件没报错」。

## 第 5 步：在真实宿主里验一次

静态检查绿了只证明**代码形状对**，不证明**插件真的能用**。起一个隔离实例装上去：

- 装、看 `--dump-config` 里有没有你的包、有没有 `did not activate`；
- 触发一次出问题的路径（那条命令、那个工具、那个面板）；
- 如果是「会话打不开」这类历史问题，**重新加载一次会话**确认不再报错。

这一步的细节走 `dsh-plugin-sandbox` 技能——不要用桌面端测，不要动用户的 profile。

## 第 6 步：让下一次更容易找到

修完回头看这两件事：

| 情况 | 做什么 |
|---|---|
| 卡片里的 `matches` 缺了你这次看到的原文 | 补进去。原文是**下一次反查的唯一抓手** |
| 规则误报了，或者漏掉了这个写法 | 改规则 + 在 `scripts/try-checks.mjs` 加一个**先红后绿**的用例 |
| 这次是新坑，`errors/` 里没有 | 按 [`references/writing-a-card.md`](references/writing-a-card.md) 写一张——先写卡片，再写检查 |

顺序不能反：**先有卡片和检查，再宣布修好了**。只改代码不留卡片，同一个坑下一个人还要再踩一遍。

## 不要做

- **不要只读卡片就改**。卡片是索引，一句话的「修法」够定位不够改对。
- **不要擅自修历史数据**。已经写坏的会话日志、已经落盘的记录，修不修是**用户的决定**；默认只保证后续不再产生。
- **不要改生成物**。契约文件、模板产物由生成器负责，改它第二天就被覆盖；改生成器或改源。
- **不要在第一个错误上停**。检查是逐条报的，常常一次有五六处同类问题。
- **不要把「没报错」当成「修好了」**。没跑第 4、5 步就是没验。
